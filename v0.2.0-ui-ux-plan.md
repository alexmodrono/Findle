# Findle v0.2.0 — UI/UX Improvement Plan

**Status:** Draft for review · **Date:** 2026-05-30 · **From:** v0.1.3

This plan covers the four areas selected for the v0.2.0 UX pass:

1. [Course detail overview](#1-course-detail-overview) — make the detail pane about *content*, not config
2. [Per-course sync status](#2-per-course-sync-status) — surface state per course, not just globally
3. [macOS conventions](#3-macos-conventions) — Settings window, ⌘, , Diagnostics placement
4. [Sync feedback & polish](#4-sync-feedback--polish) — progress, error recovery, small wins

A key finding from reading the code: **most of the data these features need already exists** in persistence and the sync engine. The work is mostly *surfacing* it, not building new model/storage layers.

---

## Data already available (the foundation)

Before the per-area plans, here's what's already queryable — this de-risks the two biggest items.

| Data | Where it lives | Notes |
|---|---|---|
| Per-course items (name, size, dir/file, parent) | `items` table — `Database.swift:174` | Full content tree + file counts + total bytes |
| Per-item download state | `items.sync_state` (`ItemSyncState`) | `placeholder` / `downloading` / `materialized` / `stale` / `error` |
| Per-course last-synced + item count | `sync_cursors` table — `Database.swift:197` | Already persisted per `(course_id, site_id)` |
| Live per-course sync progress | `SyncEngine.SyncProgress` — `SyncEngine.swift:21` | `totalItems`, `processedItems`, `state`, `fractionCompleted` |
| Per-course subscription state | `CourseSubscriptionState` — `SyncState.swift:19` | `discovered` / `subscribed` / `syncing` / `synced` / `stale` / `error` |

What's missing is **not data** — it's (a) AppState exposing it to the views and (b) a couple of small `Database` aggregate queries (e.g. `SELECT COUNT(*), SUM(file_size) ... GROUP BY course_id`).

## 1. Course detail overview

### Problem
Selecting a course is the app's primary interaction, but `CourseDetailView.swift` is a **settings form**: icon picker, folder rename, tags, a sync toggle, and an HTML-stripped summary. The actual content being synced — sections, files, sizes, freshness — is invisible. The view the app is *named for* shows none of the syncing.

### Proposal
Restructure the detail pane into a **course overview**, with customization demoted to a secondary surface.

```
┌─────────────────────────────────────────────┐
│  [icon]  Operating Systems                   │  ← CourseDetailHeader (keep)
│          OS-2026 · Visible · Sep–Jan         │
│                                              │
│  ●  Synced 4 minutes ago                     │  ← NEW: status pill row
│  142 files · 1.3 GB · 138 downloaded         │  ← NEW: aggregate stats
│                                              │
│  [ Reveal in Finder ]   [ Sync ]             │  ← NEW: primary actions, prominent
│                                              │
│  ── Contents ──────────────────────────────  │  ← NEW: section/file outline
│  ▸ Week 1 — Introduction        12 files     │     (from `items`, grouped by parent)
│  ▸ Week 2 — Processes           18 files     │
│  ▸ Lab Materials                 9 files     │
│                                              │
│  About                                       │  ← keep summary (already there)
│  …                                           │
│                                              │
│  ⚙ Customize  (folder name, icon, tags) ▸    │  ← demote to disclosure / sheet
└─────────────────────────────────────────────┘
```

Key moves:
- **Promote "Reveal in Finder"** to a primary action in the detail pane (today it's only in the window toolbar / context menu). This is the natural "I want my files" action.
- **Status + stats row** driven by `sync_cursors` (last synced) + an aggregate query over `items` (count, bytes, downloaded count).
- **Contents outline** — a collapsible list of top-level sections with file counts, read from `items` grouped by `parent_id`. Read-only in v0.2.0; the Finder remains the place to open files. (Open question: how deep to go — see below.)
- **Demote customization** (rename / icon / tags) into a "Customize" disclosure group or a sheet, so the overview leads with content.

### Files
- `CourseDetailView.swift` — restructure body; keep `CourseDetailHeader.swift` as-is (it's good)
- `AppState.swift` — add `func courseStats(for:)` / `func courseContents(for:)` accessors
- `Database.swift` — add aggregate count/size query + grouped-items fetch
- New small view(s): `CourseStatsRow`, `CourseContentsList`

### Effort
Medium. The data exists; this is view work + 1–2 DB queries + AppState wiring.

## 2. Per-course sync status

### Problem
`SyncStatus` and `syncProgressDetail` (`AppState.swift:65`, `:73`) are **app-wide**. The sidebar `CourseRow` (`CoursesView.swift:9`) shows name + tag dots but nothing about whether *that* course is up to date, syncing, or errored. During "Sync All" only the global status bar moves — if one course fails, you can't tell which.

The engine already tracks this per course (`SyncEngine.allProgress()` → `[Int: SyncProgress]`), and `syncAll` already polls it (`AppState.swift:736`) — it just collapses the result into one global number.

### Proposal
- **Expose per-course state in AppState**: publish a `[Int: CourseSyncStatus]` map (derived from `engine.allProgress()` while syncing, and from `sync_cursors`/`items` at rest). The polling loop in `syncAll` already has this data — stop collapsing it.
- **Sidebar status indicator** on `CourseRow`: a small trailing glyph — spinner while syncing, subtle error dot on failure, nothing when idle/synced (keep rows calm). Reuse the tag-dot row area.
- **Detail pane** reuses the same status in the [overview](#1-course-detail-overview) pill.

```
Sidebar row states:
  Operating Systems          (idle — clean)
  Databases            ◌     (syncing — spinner)
  Algorithms           ⚠     (error — tap to see why)
```

### Files
- `AppState.swift` — add `@Published var courseSyncStatus: [Int: ...]`; populate from existing poll loop + at-rest from cursors
- `CoursesView.swift` (`CourseRow`) — trailing status indicator
- `CourseDetailView.swift` — consume same status

### Effort
Low–medium. Mostly plumbing data that's already computed; main care is keeping the sidebar visually quiet.

## 3. macOS conventions

Three concrete HIG deviations found in the code:

### 3a. Settings is duplicated
There's a real `Settings { SettingsView() }` scene (`FoodleApp.swift:49`) — so ⌘, *should* open a standard Settings window — **but** `SettingsView` is *also* a sidebar destination inside `WorkspaceView` (`WorkspaceView.swift:226`, `:321`). Same screen, two homes.

**Proposal:** Pick the standard one. Remove Settings from the sidebar; let it live in the Settings scene opened via the app menu / ⌘,. (Keeps the sidebar purely about courses.)

### 3b. ⌘, is hijacked
The menu bar's "Open Findle…" is bound to ⌘, (`MenuBarView.swift:28`). On macOS ⌘, is *the* Settings shortcut — users will hit it expecting preferences and get the main window instead.

**Proposal:** Rebind "Open Findle…" (e.g. ⌘O, or no shortcut) and let ⌘, open Settings as users expect. Optionally add a "Settings…" item to the menu-bar menu.

### 3c. Diagnostics as a permanent sidebar item
`DiagnosticsView` is a power-user/debug screen pinned as a top-level sidebar row (`WorkspaceView.swift:229`).

**Proposal (pick one):**
- Move it behind the **Help** menu ("Diagnostics…"), or
- Make it a tab *within* the Settings window's Advanced section, or
- Keep it in the sidebar but only reveal it via a key modifier / when verbose logging is on.

### Files
- `WorkspaceView.swift` — remove Settings/Diagnostics sidebar section; simplify `SidebarSelection`
- `MenuBarView.swift` — rebind shortcut, maybe add Settings item
- `FoodleApp.swift` — possibly add `.commands` / Help menu entry for Diagnostics

### Effort
Low. These are mostly deletions + rebinding. Highest ratio of polish-per-line.

> **Note:** removing Settings/Diagnostics from the sidebar changes navigation muscle memory. Worth confirming you're happy moving Settings fully to the ⌘, window before I do it (see open questions).

## 4. Sync feedback & polish

Smaller, incremental wins:

- **Determinate progress bar.** `SyncStatus.syncing(progress: Double)` already carries a fraction (`AppState.swift:67`), but the status bar only shows an indeterminate spinner + text (`WorkspaceView.swift:271`). Swap in a thin `ProgressView(value:)` for real "how far along" feedback. Nearly free.
- **Richer error recovery.** The error banner only offers **Dismiss** (`WorkspaceView.swift:133`). For sync failures, add **Retry**; for some, a **Help/Details** affordance. The session-expired banner already does this well (`Reconnect`) — extend the pattern.
- **"Sync this course" reachability.** Currently per-course sync is in the context menu + detail toolbar; the overview's primary [Sync] button (§1) covers this.
- **Optional small touches:** count badge on "Sync All" tooltip ("3 of 12 enabled"), relative-time auto-refresh in the status bar, and a subtle success flash on completion.

### Files
- `WorkspaceView.swift` — progress bar in `statusBar`, Retry action in `banners`

### Effort
Low.

## Suggested phasing

Ordered to ship value early and keep each PR reviewable:

1. **PR 1 — macOS conventions (§3).** Smallest, self-contained, immediate polish. Settles navigation before bigger view work lands.
2. **PR 2 — Sync feedback & polish (§4).** Low-risk, isolated to `WorkspaceView`.
3. **PR 3 — Per-course sync status (§2).** Adds the AppState plumbing the overview will reuse.
4. **PR 4 — Course detail overview (§1).** Biggest; builds on the status work from PR 3.

Each is independently shippable, so v0.2.0 can land as much or as little as you want.
